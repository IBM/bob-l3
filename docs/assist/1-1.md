## **i. Editing with intent**

---

Much of a developer's day is spent making precise, surgical change to code that already exists. **Literate Coding** allows developer and users to annotate their code— using plain, natural language instructions —directly inside and inline the files they are working with. Bob then takes care of the heavy lifting by ensuring that every change is accounted for and that no instructions are missed. 

IBM Bob reads the instruction in place and produces a targeted, localized modification. The developer is still describing intent in plain language; the difference is that here you are pointing at a specific spot and saying "change *this*." Think of it like annotating changes in a collaborative Word document, where you can delegate the modifications to a trusted colleague who will shoulder the workload.

This is the first (and most gentle) stage of the **AI Maturity Curve**, and therefore a natural sweet spot for building your understanding of IBM Bob. Across this module, you'll work shoulder to shoulder with Bob from the perspective of a software developer paired with the Bob editor. As you work, Bob will be anticipating the next keystroke, drafting the next few lines, and making targeted edits upon your request — all the while keeping the developer (*you*) in control of accepting or rejecting every AI-generated proposed change.

![](_attachments/Module-1-Assist.png)
    
!!! note "AI MATURITY CURVE"
    Literate Coding is a prime example of where the *control* that the human in the loop retains with IBM Bob — as part of the **early Assist stage along the AI Maturity Curve** — becomes tangible and truly valuable. IBM Bob never silently rewrites your files or codebase. Instead, it presents every change in a *diff* view that shows the added code, the removed code, and enough surrounding context to understand the scope of what is changing. You review, then you decide on whether to implement the suggestion or disregard it. Nothing is committed until you say so.

## **ii. Why this matters**

---

Literate coding is at its best for focused, in-place work:

- **Wrapping logic** around existing code — retry mechanisms, error handling, or logging
- **Refactoring a specific block** while leaving the surrounding logic untouched
- **Quick, targeted modifications** to a single function without disturbing the broader structure

IBM Bob users engage the literate coding mode through the magic wand icon in the Bob IDE (you'll see exactly how this is performed in a few moments.) Once active, it allows those users to write natural-language instructions at a precise code location. They can target the exact section of code where changes are to be made; alternatively, they can queue up several instructions in sequence, across multiple locations of a single file.

---

**How it works**

The workflow is deliberately simple:

1. Position your cursor within the codebase where the change belongs
2. Click the magic wand icon to enter literate coding mode
3. Type a natural-language instruction describing the change you want to implement
4. For changes that span several places, add an instruction line at each location
5. Click generate to produce the modifications (across one or many instructions)

## **v. Key takeaways**

---

- Literate coding turns plain-language instructions, written in place, into precise code change
- The *diff* view keeps you in full control, allowing you to inspect and understand every change before it is committed to code
- The literate coding mode is most effective for focused, single-file modifications
- For multi-file or architectural changes, Code mode is the more appropriate tool for the job

</br>

For sweeping, multi-file changes or architectural restructuring, you will instead want to reach for IBM Bob's **Code mode**. The topic is covered extensively within <a href="https://ibm.github.io/bob-l3/delegate/2-1.md" target="_blank">**Module 2 | Delegate**</a>, which you will explore next.
