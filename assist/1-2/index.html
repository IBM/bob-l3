    MODULE 1 | ASSIST

    LITERATE CODING

    i. Editing with intent

    Tab completion and next edit prediction shine while you are writing new code. But much of a developer's day is spent making a precise, deliberate change to code that already exists — and for that, literate coding is the tool. It lets you write a natural-language instruction directly inside a file, exactly where the change belongs, much as you would jot a comment.

    IBM Bob reads the instruction in place and produces a targeted, localized modification. The developer is still describing intent in plain language; the difference is that here you are pointing at a specific spot and saying "change this."

    Watch first: Chapter 2.2: Literate Coding [IBM Bob L3]

    Maximilian Jesch (Outbound Product Manager — IBM Bob) demonstrates Bob's literate coding capabilities. [2 min]

    ii. Why this matters

    Literate coding is at its best for focused, in-place work:

    • Wrapping logic around existing code — retry mechanisms, error handling, or logging
    • Refactoring a specific block while leaving the surrounding logic untouched
    • Quick, targeted modifications to a single function without disturbing the broader structure

    IBM Bob users engage the literate coding mode through the magic wand icon in the Bob IDE (you'll see exactly how this is performed in a few moments.) Once active, it allows those users to write natural-language instructions at a precise code location. They can target the exact section of code where changes are to be made; alternatively, they can queue up several instructions in sequence, across multiple locations of a single file.

    AI MATURITY CURVE

    Literate Coding is a prime example of where the control that the human in the loop retains with IBM Bob — as part of the early Assist stage along the AI maturity curve — becomes tangible and truly valuable. IBM Bob never silently rewrites your files or codebase. Instead, it presents every change in a diff view that shows the added code, the removed code, and enough surrounding context to understand the scope of what is changing. You review, then you decide on whether to implement the suggestion or disregard it. Nothing is committed until you say so.

    How it works

    The workflow is deliberately simple:

    1. Position your cursor within the codebase where the change belongs
    2. Click the magic wand icon to enter literate coding mode
    3. Type a natural-language instruction describing the change you want to implement
    4. For changes that span several places within the codebase, add an instruction line at each location
    5. Click generate to produce the modifications (across one or many instructions)


    Going further

    For sweeping, multi-file changes or architectural restructuring, you will reach for IBM Bob's Code mode instead. This topic will covered extensively in MODULE 2 | DELEGATE, which follows this section.

    EXPECT SOME VARIABILITY

    Generative AI is non-deterministic and as such your results may differ from what you see here. If an output diverges, consider further refining the prompt, following up with another prompt, or adjusting the code by hand. Iteration and further precision are often the best remedies.

    iii. Hands-on: adding retry logic with Literate Coding

    Follow the video for a full walkthrough: Chapter 2.2: Literate Coding [IBM Bob L3]

    Galaxium's backend can be slow to respond when fetching flight information, and occasional timeouts are the result. It is a perfect candidate for a small, surgical fix: we will use literate coding to wrap the flight-fetching call in retry logic — without hand-writing any of it.

    1. Back in the IDE, open Flights.tsx\ \ (booking_system_frontend > src > pages > Flights.tsx)

    1. Click the magic wand icon near the top of the editor — or press Ctrl + I — to activate literate coding mode.

    1. A bar appears at the bottom-center of the screen with two arrows, Clear All, and Generate — you are now in literate coding mode!

    On line 43 in Flights.tsx, type:

    the backend is unreliable at times. We need a retry logic here

    The text should highlight to show the mode is active. Treat the visible mode state and the Generate button as your primary indicators, since the exact highlight color can vary by release.

    Unlike tab completion, there is no need to comment this instruction out.

    1. With the instruction written, press the Generate button.

    1. A diff view appears. Removed code is shown in red, and added code in whatever highlight your build uses for additions (yellow in this capture; some versions use green). Review the on-screen diff carefully before accepting.

    1. If everything looks right, press Accept All.

    The red lines are removed, and the new highlighted lines are written into the file.

    This particular change may not produce anything visible in the running app — and that is by design; the point is to watch targeted code generation happen in context, against real code.

    Take a moment to read what Bob produced, and then we will move on.

    Key takeaways

    • Literate coding turns a plain-language instruction, written in place, into a precise code change.
    • The diff view keeps you in full control — you see every change before it lands.
    • It is most powerful for focused, single-file modifications.
    • For multi-file or architectural changes, Code mode is the right tool — and that is where we go next.
