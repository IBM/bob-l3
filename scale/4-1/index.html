    MODULE 4 | SCALE & EXTEND

    THE CONTEXT WINDOW

    i. Keeping Bob reliable at scale

    AI MATURITY CURVE

    By the end of Module 3 | Tailor, IBM Bob knew nearly every facet about your project, adhered to your organization's coding standards, and had adapted itself to each role on your team — and all of that was committed to the repository, shared, and automatically enforced. The final stage along the AI Maturity Curve journey reflects the two things that separate a promising demo from a dependable enterprise partner: staying reliable on the largest, longest-running workloads; ultimately, connecting to everything else that your organization already runs today.

    In other words, addressing the enterprise challenges of Scale and Extensibility.

    Across this module, you will first look under the hood at the context window mechanics that make Bob tick. Arguably, the context window might be the single biggest factor in keeping Bob's output at the highest quality across the most ambitious tasks. The habits and best practices that developers (you) adopt in maximizing the utility of this resource can have tremendous impacts on the quality of work that Bob is able to perform.

    Afterwards, you'll take Bob out of the IDE entirely and into the Terminal console: Bob Shell. This programmatic interface for Bob unlocks automation, scripting, and parallelized workstreams.

    Finally, you will experiment with connecting Bob to your existing systems through Model Context Protocol (MCP), the open source standard that lets Bob interact directly with the external tools your teams use daily. Governance remains paramount at this stage. As the human-in-the-loop and final arbiter of control, you must decide what context Bob carries, what credentials it holds, and which tools it is permissioned to reach.

    ii. Why this matters

    The context window is the total amount of information a large language model can hold in mind during a single conversation. It is also the quiet determinant of quality on any substantial task — so understanding how it fills, and how to manage it, is what separates a polished demo from one that degrades halfway through. This lesson is conceptual; there are no steps to run, but the habits it instills will shape every other interaction you have with Bob.

    What a context window is

    The models powering Bob offer a context window of 200,000 tokens — roughly 150,000 words, about the length of The Fellowship of the Ring. Every conversation begins with that full capacity available, and it holds everything: instructions, file contents, conversation history, and Bob's own responses. Once the window fills, the oldest content has to be dropped or summarized to make room.

    What fills it, and in what order

    At the start of every conversation, content loads in a predictable sequence:

    Order Content Notes
    1 Bob system prompt Hidden from the user; contains Bob's core instructions
    2 Mode description The definition of the currently active mode (Code, Plan, custom, etc.)
    3 Rules Content from all files in .bob/rules/
    4 MCP tool definitions Can be very large, depending on the number and complexity of connected MCP servers
    5 Conversation messages User prompts and Bob's responses
    6 File reads and writes Contents of files Bob reads or produces during the conversation

    MCP tool definitions deserve special attention: depending on how many servers you've connected, they can consume a significant slice of the window before you send a single message — a direct link to the governance theme of this module.

    What happens when it fills

    Reaching the 200,000-token limit doesn't stop Bob or throw an error. Instead, a new conversation starts automatically in the background, Bob generates a summary of the previous one, that summary is prepended to the new conversation, and Bob carries on responding seamlessly. The process is invisible to you — but it has real consequences for quality and cost, and that is precisely why it's worth understanding.

    The two things to watch

    First, summarization is lossy. When a conversation overflows and gets summarized, specific technical details, intermediate reasoning, and nuanced context can be lost — a summary is always less precise than the original exchange. If a critical constraint or edge case was discussed early on, it may not survive into the summary, and implementation quality can suffer.

    Second, quality degrades above roughly 100,000 tokens. Models don't hold uniform quality across the full range; as the window fills, responses noticeably decline, particularly past the ~100,000-token mark. A conversation using 50,000 tokens will generally produce better output than one using 180,000, all else being equal. And because tokens are the unit of consumption (measured in Bob coins), longer conversations and larger file reads also simply cost more. Less context used means both better output and lower cost.

    The strategy: persistent artifacts

    The most effective way to manage all of this is the persistent artifacts pattern: break a complex task into discrete steps, have each step produce a saved output (a file on disk), and start a new conversation for each major step, referencing the saved output. No single conversation balloons, and every important decision is preserved as a durable file you can point back to later.

    You have already seen this in action. The seat-class feature from Module 2 was built exactly this way:

    Conversation Task Output
    1 Plan the feature seat-class-implementation-plan.md, seat-class-architecture.md
    2 Implement based on plan Code changes across frontend, backend, and database

    The implementation conversation consumed just 88,000 of 200,000 tokens — comfortably within the high-quality range — because the two-conversation split kept the planning discussion from competing with the implementation for space.

    A few practical guidelines fall out of all this: start new conversations when you switch tasks (planning shouldn't bleed into implementation); prefer direct file references (@/path/to/file) over pasting contents; keep MCP configurations lean, since every server's definitions cost context on every start; and monitor token usage to see which interactions are most expensive and adjust accordingly.

    Key takeaways

    • The context window is 200,000 tokens (~150,000 words) — every conversation starts fresh with this capacity.
    • Context fills in order: system prompt → mode description → rules → MCP tools → messages → file reads/writes.
    • When context is exhausted, Bob auto-summarizes and continues — but summarization is lossy.
    • Quality noticeably degrades beyond ~100,000 tokens.
    • The persistent-artifacts pattern (plan → save → new conversation → implement) is the primary strategy for managing context.
    • Less context used means better output quality and lower cost.
